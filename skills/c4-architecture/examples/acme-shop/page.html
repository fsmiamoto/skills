Architecture · C4 model · fictional example

Acme Shop, from the cloud down to the checkout.

Acme Shop is a small online store. A React storefront calls one API service; a worker built from the same image handles everything that must happen after a commit: payment capture, emails, stock release. Postgres holds orders and an outbox, and a managed queue carries jobs between them.

Level 1 · System context

Who uses Acme Shop, and what it talks to

The shop owns the catalog, carts and orders. It never stores card numbers: a payment provider holds them and reports back by webhook. An email service sends the messages.

What is true today

  • Two kinds of people. Shoppers need no account to buy; staff sign in and get the staff role. {{src:api/src/acme/auth/roles.py|auth/roles.py}}
  • No card data in the shop. The storefront confirms cards in the provider's widget; the API only sees payment intent ids. {{src:api/src/acme/payments/client.py|payments/client.py}}
  • Webhooks are signed. Unsigned or replayed calls are rejected before any order changes. {{src:api/src/acme/payments/webhooks.py|payments/webhooks.py}}

Level 2 · Containers and cloud infra

Two containers, one database, one queue

Staging and prod are separate cloud accounts with the same shape, both built from infra/ by Terraform.

Runtime topology

What serves a request, and where the state lives.

What is true today

  • One image, two modes: the entry point starts the HTTP server or the worker loop. {{src:api/src/acme/main.py|main.py}}
  • Postgres 16, managed, private network only; daily backups kept 7 days. {{src:infra/database.tf|infra/database.tf}}
  • The queue delivers at least once, so every job handler is idempotent. {{src:infra/queue.tf|infra/queue.tf}}

Delivery

From a merge to running containers.

  • One pipeline file covers web and API. {{src:.ci/pipeline.yml}}
  • Deploys are by digest, never by a moving tag. {{src:infra/deploy.tf|infra/deploy.tf}}

Level 3 · Components

Inside the API service

One Python package per component under api/src/acme/. Routes stay thin; services hold the rules; only db touches SQL.

What is true today

  • Import rules are checked in CI: routes may not import db. {{src:api/importlinter.ini|importlinter.ini}}
  • checkout runs the whole order placement in one transaction. {{src:api/src/acme/checkout/service.py|checkout/service.py}}
  • orders rejects any transition not in its table. {{src:api/src/acme/orders/states.py|orders/states.py}}

Built vs planned

Every diagram above shows only what exists in code today. These are written down in {{src:docs/roadmap.md|roadmap.md}} but not built.

Live In code and running

  • Guest checkout with card payments
  • Order states, staff cancel and refund
  • Outbox worker for capture, refunds and email
  • Staging and prod accounts from one Terraform config

Planned Documented, not built

  • Shopper accounts and saved addresses
  • Partial refunds
  • A second worker replica with per-kind queues
